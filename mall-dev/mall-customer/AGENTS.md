# mall-customer 后续开发约定

## 当前开发顺序（用户于 2026-11-14 确认）

后续修改优先搭建并跑通 Python Agent 的基础运行体系，再补充外部业务能力。此约定更新此前一次性贯通 Java、工具与前端的实施顺序；此前实施记录保留为历史事实。

1. 先完善记忆边界、State、子 Agent 设计、图结构、Agent Loop、checkpointer，以及中断和恢复等基础条件，形成可独立验证的运行闭环。
2. Java 后端业务接口接入、具体 tool 服务和 RAG 功能在后续与用户一起补充，当前不要主动扩展这些能力。基础流程验证可以使用明确标注的测试替身或本地样例，不能将其描述为真实业务接入或真实操作成功。
3. 已有业务接入代码不因本约定自动删除或重写；需要调整时，以当前阶段的基础运行目标为依据。

## 数据访问方向

- 用户、商品、订单、售后等业务数据查看统一通过 Java 服务，由 Java 负责查询业务数据库、身份与数据归属校验及业务规则。
- Python 通过 Java 提供的服务接口获取所需业务数据，不直接连接商城业务数据库，也不采用 Java/Python 共享访问业务表的方案。
- Python 的执行检查点或后续商定的记忆存储属于 Agent 运行基础设施；它们与商城业务数据库的访问职责分别设计。

## 延续的设计约束

- 主干采用 Supervisor + 专业子 Agent，子 Agent 结果返回 Supervisor 继续决策。
- 两个业务子 Agent 为“商品与规则咨询 Agent”和“订单与售后 Agent”；后续围绕基础运行体系完善其职责与状态流转。
- State 承载工作状态，不额外叠加无必要的 WorkingMemory。长期、短期记忆的具体模型仍需与用户商讨，不能把 checkpointer 持久化等同于已完成记忆设计。
- 人工中断覆盖敏感操作、用户明确要求人工、自动审查有限修正后仍不通过；先保证图中的暂停与恢复机制成立，业务接口后续补充。
- 项目模型提示词使用中文。
- 所有项目修改限定在 `G:\study_code\text\java+ai\mall-dev` 内，参考项目只读。
